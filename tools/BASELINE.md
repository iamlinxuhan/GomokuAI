**哪些数字可复现，哪些不可 —— 这一点必须说清。**

`_check_win_fast` 在 `alpha_beta` 里每节点调用两次（入口判己方、判对手各一次），
每次全盘扫描约 1170 次单元读取，这是 70% 左右耗时的来源 ——
**热点排序与量级占比是稳定信号**，三次独立测量都指向同一结论。

但**绝对调用次数不稳定**。上一轮（改动前，`main.py` 现场）测得的是
17,861,038 次 / 8.311 s，比本次高约 20%。原因是旧引擎的 Zobrist 表：

```python
_zobrist_table = np.random.randint(0, 2**63, size=(2, 19, 19), dtype=np.uint64)
```

它在 **import 时**用未播种的 `np.random` 生成 → 每次进程的表都不同 →
TT 键与碰撞模式不同 → 搜索树大小不同。本目录的工具在 `load_engine()` **之前**
调用 `np.random.seed()`，因此本目录内的数字可复现；跨环境比较时应只看
比例而非绝对值。

深度由时间预算驱动，而 cProfile 会拖慢约 2-3×，所以即使同一局面，
"8 秒内到达的深度"在开/关 profiling 时也会差一层。

复现冒烟（同一局面，逐难度递增）：`0.368s / depth 2` → `3.445s / depth 4`
→ `8.171s / depth 5`。与上表同批测量。

## 附带发现：旧引擎结果依赖调用顺序

旧引擎把 TT / `_history_table` / `_killer_moves` / `_eval_cache` 全放在
**模块级全局**，于是同一局面的搜索结果取决于此前跑过什么：

```
单独跑 level 3 于 B1  →  走 K9   （val = -10840.5）
先跑 level 1、2 再跑 3 →  走 H13  （val = +14938.8）
```

两者都不对，但**结果不一致本身就说明状态在泄漏**。因此：

- `tests/conftest.py` 的 `_isolate_legacy_globals` 在每个用例前后清空这些全局；
- `tools/positions.py` 的 `reset_engine()` 在每个局面之前重置
  （新引擎走 `new_game()`，旧引擎走显式清空），
  **否则 A/B 对比的就不是算法差异，而是"谁捡到了更暖的缓存"**；
- `tools/selfplay.py` 每局开始同样重置。

### Phase 1 的自对弈门槛：为什么它在这里不适用

方案给 Phase 1 定的门槛是"新 vs 旧自对弈胜率 45-55%"。实测两次
（`--games 4 --no-swap` 得 66.7%，`--games 8` 交替执黑得 28.6%），
**两个数字都不该被当成结论**，理由如下：

1. **胜负由执黑决定，而非引擎。** 8 局里黑方赢 6、白方赢 1、和 1。
   五子棋先手优势压过了一切其他因素。
2. **`--swap` 并没有构成配对比较。** A 执黑的四个开局是
   (8,8)/(8,10)/(9,8)/(10,9)，B 执黑的是 (8,9)/(8,11)/(9,10)/(10,10) ——
   八个互不相同的开局，没有任何一局被两种执色各走一遍。
3. **n=8 太小。** 2 胜 5 负 1 和的 95% 置信区间宽到覆盖 50%。

真正能定论的检查是**逐手回放**：取那局 111 手的完整棋谱，在每一个局面上
分别问两个引擎"你走哪里"（各自重置状态）：

```
回放 111 手，逐手比对（level 1，双方各自重置状态）
  全部 110 个局面：两个引擎选点完全一致
```

**110 个局面无一分歧。** 所以这次搬迁没有引入行为差异，胜率的抖动是抽样
噪声而非回归。这也回过头解释了为什么 `test_engine_parity.py` 足以充当
Phase 1 的护栏，而自对弈胜率在 n=8 时做不到。

（回放脚本是一次性检查，未纳入测试套件：110 个局面 × 2 个引擎约需 90 秒，
而 Phase 2 起这些等价性测试会整体删除，不值得让套件长期背着这个成本。）

### 冒烟测试查出的新缺陷（B23）

**`_on_restart` 会崩掉整个程序。** `_on_restart()` 关闭 logger 后，上一局
仍在运行的 AI 线程返回结果，`_on_ai_finished` 往已关闭的文件写日志 →
`ValueError: I/O operation on closed file` → 异常在 Qt 槽里传播 → 进程
**core dump**。

`_ai_generation` 校验本应拦下它，但只有 `_start_game` 会重置代数，
`_on_restart` 这条路径不递增，于是陈旧结果照常通过。修法：

- `_cancel_ai()` 在**等待之前**先递增代数 —— 等待有超时上限，超时后线程
  仍在跑，它的结果稍后必会投递回来，必须提前作废；
- `_start_game()` 由"重置为 0"改为**递增** —— 重置回 0 反而危险，某个迟到的
  结果可能正好持有重置后才会出现的编号而被放行；
- `_on_ai_finished` 加 `not self.logger.f.closed` 作纵深防御。

这类 bug 只有"真的点一次重开"才会暴露，静态检查与算法测试都覆盖不到 ——
这正是冒烟测试存在的理由。

### 引擎耗时的突变点

难度 3 的搜索耗时随盘上子数**突变**，写测试时必须知道：

| 盘上子数 | 耗时 | 深度 |
|---|---|---|
| 2 | 14 ms | 0（评估认为无可搜之物，直接返回） |
| 4 | 8252 ms | 5 |
| 6-14 | 约 7.8-8.4 s | 5 |

因此"AI 正在思考"这个状态不能靠点击后立刻判断 —— 2 子时会在 14ms 内自己
结束。`gui_smoke.py` 用"点击后 pump 150ms 仍 `ai_thinking`"来区分"瞬回"与
"真在搜"。

## Phase 2 完成记录（棋盘原语）

新增 `engine.py` 的"位棋盘核心"段：`Board` 类（361 位整数位图 + 全增量状态）
与四张模块级预计算表。旧搜索代码原样保留 —— Phase 3+4 会整体替换它们，
过渡期间两套胜负判定并存。

### 实测（60 子中局，同一局面）

| 项 | 旧 | 新 | 倍数 |
|---|---|---|---|
| `check_win`（公开接口，含 ndarray→位图转换） | 231.4 µs | **2.26 µs** | **102×** |
| `has_five`（纯位运算，无转换） | — | **0.89 µs** | 达标（目标 <1 µs） |
| `makes_five`（增量，只查过该点的窗口） | — | 0.67 µs | |
| `make`（繁忙区域 / 空旷区域） | — | 1.4 / 2.7 µs | |
| `make` + `unmake` 往返 | — | 2.84 µs | |
| `import engine` | ~16 ms | 24.7 ms | 建表 +9 ms |

**"<1 µs"这个目标要分清是哪一个。** `has_five` 是 0.89 µs，达标；公开的
`check_win` 是 2.26 µs，多出来的 1.4 µs 全在 `np.packbits` 把 19×19 数组
转成位图这一步。UI 每次落子只调一次，这个差距无所谓；搜索内部不走这条路
（它直接用 `Board`），所以真正的热路径是 0.89 µs 那一档。

对照 Phase 0 基线里记的 367 µs：那是**另一个局面**，与本表的 231.4 µs
不可直接比较。同局面同方法的对照才是有意义的那个数字。

### 表结构不变式

`_LINE_MASKS` 各方向线数 `[19, 19, 37, 37]` = 112 条；每格恰在 4 条线上；
连五窗口合计 5100（中心格 20 个、角格 3 个）；邻域半径 2 的邻居数
中心 24、角 8。这些是几何事实，`tests/test_incremental.py` 对它们有断言，
防止后续改动让表的语义悄悄漂移。

### 换行陷阱（`_FIVE_STARTS`）

全盘连五检测用 `bits & bits>>s & bits>>2s & ...`，而线性索引
`idx = r*19 + c` 会把**行末与下一行行首接在一起**：idx 15,16,17,18,19 连续，
但 (0,18) 与 (1,0) 在几何上毫不相干。所以必须用 `_FIVE_STARTS[d]` 把
"从这个位置起的 5 格会跑出线外"的起点滤掉，否则
`(0,15)(0,16)(0,17)(0,18)(1,0)` 会被判成五连。

`tests/test_win.py` 对此有专门的回归用例（三个方向各一条），
并配了反向用例确保滤网**不会**把真实的边缘五连一起滤掉。

### 途中查出的一个污染路径

`Board.make(idx, p)` 若收到 `np.int64`（`np.argwhere` 的返回值极易被直接
传进来），`1 << idx` 会得到 numpy 标量，于是 `cand_mask` 被静默换成
numpy 类型；等某次位移 ≥63 位时才抛
`OverflowError: Python int too large to convert to C long` —— 报错点离
真正的原因隔了很远，而且此时状态已经污染了。

修法是 `make`/`unmake` 入口 `idx = int(idx)` 收口。这不是防御性编程洁癖：
numpy 整数混进位运算是个**静默**失效路径，不报错的那段时间里搜索只是在
偶尔选错着法。

### 有意保留的行为变更

空盘时 `Board.candidates()` 返回**天元一个点**，而旧 `_generate_moves`
在候选为空时退化为"全部空格"。这不是等价替换：空盘的开局着法归 Phase 3 的
根节点处理，原语层只需要给出一个合法着法。`tests/test_incremental.py`
把这个差异写成显式断言，免得日后被当成 bug"修"回去。

### 验证

```bash
.venv/bin/python -m pytest tests/test_win.py tests/test_incremental.py -q   # 58 passed
.venv/bin/python -m pytest -q                                               # 91 passed, 3 xfailed, 7 xpassed
```

`test_incremental.py` 是这一阶段的核心护栏：随机对局**每落一子**都把
增量维护的候选集 / 邻居计数 / 哈希 / 子数与**完全独立的朴素实现**逐项比对，
再做逐层 make-unmake 还原、乱序撤销、部分乱序撤销后与重建比对。
增量代码的失效模式是"状态只是稍微不对，搜索照样跑得动"，逐项差分是唯一
能抓住它的办法。

## Phase 3+4 完成记录（评估与搜索整体替换）

旧 `evaluate_board` / `alpha_beta` 与其全部辅助函数已删除，换成：位棋盘的
全增量线评分、严格零和评估、negamax + PVS + 置换表 + 静止搜索 + 历史/杀手

### 棋型定义的变更（这是重写的核心）

旧版把棋型压成三元组 `(count, open_ends, has_jump)`，于是 `.XX.X.` 与
`.X.XX.` 落在**同一个 key** 上；`_SCORE_TABLE[(3, True, True)] = 1e6` 又把
"单个跳活三"抬到与活四同级、是活三的 100 倍。B1 那 0.9% 的排序差距就来自
这里。

新定义只数一个集合：`F(S) = {空点 e : 在 e 落子即成五}`，`|F|≥2` 是活四、
`|F|=1` 是冲四。**数个数是精确的**，不需要先定义"什么算活四"。

### 实测（`tools/bench.py --engine engine`，5 个局面）

> **⚠️ 下面这张表已作废（2026-09-19）。** 它是在 `engine._ZOBRIST` 退化成

## Phase 5 完成记录（Quiescence + VCF）

新增 `Engine.vcf` / `_vcf` / `_vcf_defence`。要点：

- **三态返回** `VCF_WIN=1` / `VCF_NO_WIN=0` / `VCF_EXHAUSTED=-1`。
  `EXHAUSTED`（"这套方法算不完"）**绝不可当 `NO_WIN`**（"没有杀"）用 ——
  旧 `_find_forced_win` 正是这么错的（B15）。
- **防守侧 AND 语义**：对手**所有**应手都输才算赢。旧版攻防两侧都用 OR，
  于是一条对手能挡住的线路也被报成必胜（"进攻方假必胜"）。
- **四不能胜五**：进攻节点上若对手有成五点，该节点立即 NO_WIN。
- **三重预算**：节点上限 12 万 / `VCF_MAX_PLY=24` / 独立时间，且时间
  用 `min(自身 deadline, 主搜索 deadline)` 收口。
- **根节点策略是兜底而非抢先**：VCF 证明的杀在搜索结束后**只在比搜索结果
  更长时**才被采用（`best_val < vcf_win[1]`），因此更短的（更安全的）杀
  不会被一条更慢的 VCF 线路顶掉。

## 中级档时限 5.0 → 7.0（2026-09-23）

对象是 `game_log_20260922_235240.txt`：**2 档执白、人类第 31 手 J8 胜**。
上面「已知代价」那段记的是"中级 4.25 秒预算在同一局面也只到第 4 层"，源头
就是这局。本节是它的处理结果，也把上面那句话**改写成更准确的说法**：不是
"只到第 4 层"，而是**在两种答案之间翻面**（见下）。

### 病灶与量化

胜负手在**第 4 手**（盘面 `*K8 OJ9 *K10`，白该走）。把这一手钉死、其余着法
仍用旧预算重放（`tools/pivot_ab.py --budget 5.0`），相邻两层给出胜负相反的
结论：

| 第 4 手 | 结局 |
|---|---|
| K9（第 4 层的选择） | 黑胜 · 第 31 手 J8 —— 与日志**逐手相同，31 手一手不差** |
| K7（第 5 层的选择） | 白胜 · 第 12 手 J7 |
| K11（同属第 5 层） | 白胜 · 第 18 手 J8 |

K9 那一行把原局**完整复现**（31 手全部相同，连人类致胜的那一手都相同），所以
这一手就是全局胜负手，后面 27 手都只是症状。分值为 `val=−1000`（第 4 层）/
`−170`（第 5 层）。**这条对照之所以可信，正因为它能原样复现败局** —— 一个
复现不出原局的实验，也没资格说"这一手是病根"。

**旧预算不是"差一点深度"，是压在临界点上。** 同一份输入、同一个 5.0 s 预算，
重复搜这一手会给出两种答案（`--stability`）：

| `time` | 预算 | 第 4 手实测 |
|---|---|---|
| 5.0（旧值） | 4250 ms | K7·5 层 与 K9·4 层 交替 —— 分三批测出 3/12、0/8，**起 6 个满载进程后 4/4 全走 K9** |
| 6.0 | 5100 ms | K7 · 5 层，5/5 |
| **7.0** | 5950 ms | K7 · 5 层 · val −170，4/4 |

5.0 那一行的**三批数字本身就是结论**：比例随机器当时多忙而变，稍忙就固定
翻成败着。取 7.0 的理由不是"够得着第 5 层"（6.0 就够），而是相对实测的第一
稳定点 6.0 留约 0.85 s 余量，买"不随负载翻面"。

### 三个被推翻的假设（记录下来，免得再走一遍）

本轮先报过两个"引擎缺陷"，动代码前逐条复验，**两条都不成立**：

1. **"`_vcf_defence` 返回 -1 是已证明的必败，引擎却把它丢掉"** —— 错。
   候选集只是"对手可以用来做四的格点"，挡点可能在集合之外，也可以靠反冲四
   解，所以 `-1` 不蕴含必败；`test_vcf_defence_does_not_invent_a_score`
   正是把"防守分支不许报杀棋分"写成断言。
2. **"渴望窗口的失败回退太慢是病根"** —— 冷 TT 下 `_ASP_FAILS=1` 确实让
   引擎选到胜着（K7，第 5 层），但整局重放**仍然输**。真实对局是热 TT，热/冷
   两种上下文里第 5 层最后一枪都被砍掉；差别只是冷 TT 恰好差 20 ms 完成。
   **孤立局面上的复现不能替代整局重放** —— 这条值得记住。
3. **"5.0 s 差约 100 ms 到不了第 5 层（第 5 层最后一枪要 4753 ms / 加前四层
   5202 ms）"** —— 错，而且错得最有教育意义。那个数字来自一个**与别的搜索
   并发跑着**的临时脚本，量到的是当时机器的争用，不是这个局面的成本。同一份
   输入重复实验：4250 ms 内走完第 5 层是常态（12 次里 9 次）。真实情况是
   **压在临界点上、随负载翻面**，不是"差一点"。
   **测量时间预算制的搜索时，机器上不能有别的负载** —— 否则量到的是负载。
